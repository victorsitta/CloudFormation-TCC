# Security Model

---

## Overview

The system implements a layered security model with four distinct enforcement points. Each layer provides independent protection, so a failure at one layer does not compromise the overall security posture.

```
┌──────────────────────────────────────────────────────────┐
│  Layer 1: Transport                                      │
│  HTTPS/TLS enforced on all API Gateway endpoints         │
└────────────────────────┬─────────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────────┐
│  Layer 2: Authentication                                 │
│  JWT presence validated by API Gateway (401 if absent)   │
│  JWT decoded and tenant verified by Lambda               │
└────────────────────────┬─────────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────────┐
│  Layer 3: Authorization                                  │
│  IAM roles enforce least-privilege per Lambda function   │
│  S3 access scoped to tenant prefix via IAM conditions    │
└────────────────────────┬─────────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────────┐
│  Layer 4: Encryption at Rest                             │
│  KMS CMK encrypts all S3 objects and DynamoDB data       │
│  Automatic annual key rotation                           │
└──────────────────────────────────────────────────────────┘
```

## Multi-Tenant Isolation

### Isolation Mechanism

Every request carries a JWT issued by Supabase Auth. The JWT contains a custom `tenantId` claim that identifies the tenant organization. The `access-verifier` Lambda extracts this claim and uses it to scope all AWS operations to that tenant's data.

**Isolation enforcement points:**

1. **Pre-signed URL scope** — the URL generated by the Lambda points explicitly to `s3://{bucket}/{tenantId}/{documentId}/{filename}`. The client cannot alter the key prefix.

2. **DynamoDB ownership check** — on download, the Lambda queries DynamoDB and compares the document's stored `tenantId` against the JWT `tenantId`. A mismatch returns HTTP 403 immediately.

3. **IAM key prefix condition** — the Lambda's IAM role restricts S3 access to `{projectName}-{env}/*` and the Lambda itself enforces the tenant prefix in all generated keys.

### Cross-Tenant Access Attempt

If Tenant A attempts to access a document belonging to Tenant B:

```
Request: GET /documents/download-url/doc_TENANT_B_DOC
JWT: { tenantId: "tenant_a" }

DynamoDB lookup result: { tenantId: "tenant_b", ... }

Comparison: "tenant_a" ≠ "tenant_b"

Response: HTTP 403 — Access denied: tenant mismatch

CloudWatch log:
{
  "level": "WARN",
  "operation": "GENERATE_DOWNLOAD_URL",
  "status": "DENIED",
  "reason": "tenant mismatch",
  "tenantId": "tenant_a",
  "documentId": "doc_TENANT_B_DOC"
}
```

## IAM Least-Privilege Roles

Each Lambda function has a dedicated IAM role with the minimum permissions required for its specific operations.

### access-verifier Role

| Permission | Resource | Purpose |
|-----------|----------|---------|
| `s3:GetObject` | Standard + Glacier buckets | Generate download pre-signed URLs |
| `s3:PutObject` | Standard bucket | Generate upload pre-signed URLs |
| `kms:GenerateDataKey` | CMK (via S3 service) | S3 SSE-KMS encryption |
| `kms:Decrypt` | CMK (via S3 service) | S3 SSE-KMS decryption |
| `logs:CreateLogGroup/Stream/Events` | Lambda log group | CloudWatch logging |

### metadata-handler Role

| Permission | Resource | Purpose |
|-----------|----------|---------|
| `dynamodb:GetItem` | Documents table | Fetch document by ID |
| `dynamodb:PutItem` | Documents table | Create document metadata |
| `dynamodb:UpdateItem` | Documents table | Logical delete |
| `dynamodb:Query` | Documents table + TenantIndex GSI | List tenant documents |
| `kms:GenerateDataKey` | CMK (via DynamoDB service) | DynamoDB encryption |
| `kms:Decrypt` | CMK (via DynamoDB service) | DynamoDB decryption |
| `sns:Publish` | Events topic | Publish UPLOADED/ERROR events |
| `logs:CreateLogGroup/Stream/Events` | Lambda log group | CloudWatch logging |

### archive-trigger Role

| Permission | Resource | Purpose |
|-----------|----------|---------|
| `dynamodb:UpdateItem` | Documents table | Update storageClass to GLACIER |
| `kms:GenerateDataKey` | CMK (via DynamoDB service) | DynamoDB encryption |
| `kms:Decrypt` | CMK (via DynamoDB service) | DynamoDB decryption |
| `sns:Publish` | Events topic | Publish ARCHIVED event |
| `logs:CreateLogGroup/Stream/Events` | Lambda log group | CloudWatch logging |

> The `archive-trigger` role has no S3 permissions. It only reacts to S3 events — it does not need to read or write files.

## Encryption at Rest

| Resource | Encryption | Key |
|----------|-----------|-----|
| S3 Standard bucket | SSE-KMS | CMK `alias/docsaas-key-{env}` |
| S3 Glacier bucket | SSE-KMS | CMK `alias/docsaas-key-{env}` |
| DynamoDB table | AWS KMS | CMK `alias/docsaas-key-{env}` |

**KMS key policy** restricts usage via `kms:ViaService` conditions — the key can only be used when the request originates from S3 or DynamoDB services, not directly from Lambda code.

## Logical Deletion and Audit Trail

Documents are never physically deleted from S3. When a `DELETE /documents/{documentId}` request is received:

1. DynamoDB `deleted` attribute is set to `true`
2. `deletedAt` timestamp is recorded
3. `deletedBy` user ID is recorded
4. The document disappears from all `GET /documents` responses
5. The file remains in S3 indefinitely

This approach supports audit requirements and data retention compliance (e.g. LGPD).

## Audit Logging

All Lambda invocations write structured JSON logs to CloudWatch with a consistent schema.

**Successful access:**
```json
{
  "level": "INFO",
  "message": "Pre-signed upload URL generated",
  "timestamp": "2024-03-15T14:30:00.000Z",
  "tenantId": "tenant_acme_corp",
  "userId": "user_xyz789",
  "documentId": "doc_ABC123",
  "operation": "GENERATE_UPLOAD_URL",
  "status": "APPROVED"
}
```

**Access denied:**
```json
{
  "level": "WARN",
  "message": "Cross-tenant access attempt blocked",
  "timestamp": "2024-03-15T14:30:00.000Z",
  "tenantId": "tenant_acme_corp",
  "userId": "user_xyz789",
  "documentId": "doc_OTHER_TENANT",
  "operation": "GENERATE_DOWNLOAD_URL",
  "status": "DENIED",
  "reason": "tenant mismatch"
}
```

**Log group:** `/aws/lambda/docsaas-{environment}` — 30-day retention.

## Known Limitations (Academic Scope)

| Aspect | Current Implementation | Production Recommendation |
|--------|----------------------|--------------------------|
| JWT validation | Decode only (no signature verification) | Verify RS256 signature with Supabase JWKS endpoint |
| Secrets | Environment variables | AWS Secrets Manager |
| Rate limiting | None | AWS WAF with rate-based rules |
| Network isolation | Lambda outside VPC | Lambda in private subnet with S3/DynamoDB VPC Endpoints |
| Distributed tracing | None | AWS X-Ray |
